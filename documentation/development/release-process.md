# Release Process

Releases are fully automated on merge to `main`:

1. `nx release --skip-publish` determines and writes each ic-suite package's version from conventional commits and prepends the release to that package's `CHANGELOG.md`, without committing either. Each changelog ships inside its package, so npm and GitHub Packages show it too.
2. [semantic-release](https://semantic-release.gitbook.io/) bumps the root `package.json` version, updates `CHANGELOG.md`, and commits both together with the package versions and changelogs from step 1, so a release lands on `main` as a single `chore(release): 🔖 tag codebase <version>` commit after the change itself. It then tags that commit `v<version>` and creates the GitHub release. This is the 🔖 Tag Codebase step.
3. Each newly versioned package is tagged `<project>@<version>` on that release commit. The tags are pushed six at a time, because GitHub rejects a push to this repository that updates more than six refs, and a rejected push is retried up to three times. If tags are still missing when the run ends, the next run's 🏷️ Version Packages pushes them on the same release commit before Nx reads the tags: Nx takes each package's current version from its tag, so an untagged version would otherwise be released again. When the codebase itself has no release (for example, a package-scoped `no-release` commit that Nx still bumps), the package versions are committed on their own first, as `chore(release): 🔖 tag packages`. This is the 🔖 Tag Packages step.
4. `pnpm -r publish --provenance` publishes every package in the Nx release group whose version is not on npm yet, each with an npm [provenance attestation](https://docs.npmjs.com/generating-provenance-statements) linking it to the commit and workflow run that built it. pnpm honors provenance only as that flag, which is why this step uses pnpm rather than `nx release publish`.
5. Each package is mirrored to GitHub Packages, which lists it in the repository's Packages sidebar. That registry accepts only the owner's scope, so `@codometer/cli` is mirrored as `@organizzolini/codometer-cli`, and installing from it needs a GitHub token even for a public package: npm stays where the packages are installed from. A newly mirrored package can start out private, as `codebase-devcontainer` did, and its visibility can only be changed in its package settings, not through the API.
6. Each version on npm gets a storage record on the organization's Linked artifacts page, naming npm as its registry, its npmjs.com page, the SHA-256 of its tarball, and this repository. The versions published in that run also get a GitHub build-provenance attestation from `actions/attest`; one an earlier run published is recorded but not attested, since an attestation says the run attesting it built it.

A release run takes long enough that another pull request often merges while it works. When `main` moves under it, the run steps aside rather than failing on a rejected push: the step that notices sets `RELEASE_SUPERSEDED` for the rest of the job, nothing more is pushed, tagged or published, and the newer commit's own run releases everything this one would have. Steps 1 and 2 check before they start, and steps 2 and 3 check again when a push to `main` is rejected.

Nx release owns the independent ic-suite package versions (tagged `<project>@<version>`, with each package's history in its own `CHANGELOG.md`); semantic-release owns the single codebase version (tagged `v<version>`, and the only GitHub releases made from here on, so the Latest one is what the README version badge shows). Each package's README carries an npm version badge. The first ic-suite versions were also given GitHub releases of their own, before changelogs replaced them; those stay as they are.

A new publishable package needs `"version": "0.0.0"` added to its `package.json` by hand: the conformetry templates leave `version` out, because Nx owns it once the package is released and a pinned value would fail conformance on every bump. Nx and `npm publish` both need the field. Nx treats the manifest version as the one already released: with no `<project>@<version>` tag yet, it bumps from that version using the package's whole commit history. Starting at `0.0.0` makes the first release `0.0.1` when that history resolves to a patch, which covers `feat` and `fix` commits on a `0.x` package. A breaking change in the history makes it `0.1.0` instead.
